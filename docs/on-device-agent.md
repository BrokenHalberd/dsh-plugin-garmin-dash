# 全鸿蒙本地化方案调研：把"DSH + 佳明插件"做进 App

> 调研日期：2026-10-21 · 目标：不依赖远程后端，由鸿蒙应用全权处理（数据、图表、对话）
> 结论基于**本机 SDK 实测**（非猜测）· SDK：`E:\DevEcoStudio\sdk\default`

## 一、先回答"能不能把 DSH 直接塞进 App"

**不能（直接塞）** ✗ —— 事实依据（本机 SDK 扫描）：

| 检查项 | 结果 |
|---|---|
| 存在 `@ohos.node` / `quickjs` / `v8` / `jsengine` 模块 | **✗ 全无**（只有 `@ohos.arkui.node` 这种同名干扰项 ✓ 与 JS 引擎无关 ✗） |
| DSH 的实现形态 | **Node.js CLI**（`@deepseek-ai/dsh`，靠 Node 运行时 + 子进程 + fs/net 模块） |
| 鸿蒙应用可用运行时 | **ArkTS**（TypeScript 方言，无 Node 内置模块 ✗ 无子进程 ✗ 无 npm 生态 ✗） |

→ **DSH 无法原样运行在鸿蒙上** ✗

## 二、但"全权本地处理"是**可行的** ✓ —— 换一条路

真正的差别不在"能不能跑 DSH"，而在"**我们到底需要 DSH 的哪部分**"：

| DSH 提供的能力 | 佳明场景是否需要 | 鸿蒙能否本地实现 |
|---|---|---|
| LLM 对话（API 调用） | ✅ 需要 | ✅ `@ohos.net.http` 直接调 ✓ |
| **流式输出（SSE）** | ✅ 需要 | ✅✅ **`http.requestInStream` + `on('dataReceive')` → 真流式** ✓ |
| 工具调用（function calling） | ✅ 需要 | ✅ 自己实现调度 ✓ |
| 佳明数据工具 | ✅ 需要 | ✅ 已是纯 HTTP ✓ |
| 文件读写 | ✅ 需要 | ✅ `@ohos.file.fs` ✓ |
| 记忆/会话 | ✅ 需要 | ✅ `preferences` + JSON 文件 ✓ |
| Shell / 子进程 | ❌ 不需要 | — |
| Web 搜索 / 抓取 | ⚠️ 可选 | ✅ http 可实现 ✓ |
| 子代理 / MCP / 插件系统 | ❌ 不需要 | — |

**结论** ✓：要做的是**一个"最小 Agent 内核"**（LLM 循环 + 工具注册 + 记忆），
不是"把 DSH 移植过来" ✓ —— 工作量可控 ✓ 且**功能上更干净** ✓

| 能力 | 模块 | 实测 |
|---|---|---|

| WebSocket | `@ohos.net.webSocket` | ✅ 存在 ✓ |

| JSON / 编码 | `@ohos.util` | ✅ 存在 ✓ |
| 本地存储 | `@ohos.data.preferences` | ✅ 存在 ✓（放 API Key / 会话 ✓） |
| 文件系统 | `@ohos.file.fs` | ✅ 存在 ✓（放记忆库 / 缓存 ✓） |

**关键发现** ✓✓：**流式在我们自己的 App 里是可行的** ✓ ——
之前"流式失败"是**后端 DSH 插件框架**的限制 ✗（它不接受分段写响应 ✓），
而**设备侧是客户端** ✓ 用 `on('dataReceive')` 逐块读取 ✓ **天然支持 SSE** ✓✓

## 四、推荐方案（三档，按投入排序）

### 方案 A · 纯 ArkTS 最小 Agent 内核（**推荐** ✓）
```
用户提问
  → 构造 messages（system + 历史 + 本轮）
  → POST LLM /chat/completions（stream: true）
  → on('dataReceive') 解析 SSE → 逐 token 渲染 ✓✓
  → 若返回 tool_calls → 本地执行工具（Garmin HTTP / 读文件 / 查缓存）
  → 把工具结果回填 messages → 再次请求（循环，最多 N 轮）
  → 落盘会话（preferences + JSON）
```
| 项 | 评估 |
|---|---|
| 工作量 | **中**（核心约 600~900 行 ArkTS ✓：SSE 解析 ✓ 工具注册 ✓ 循环 ✓ 记忆 ✓） |
| 依赖 | **零** ✓（无 Node ✓ 无后端 ✓ 无第三方 SDK ✓） |
| 能力 | 数据问答 ✓ 图表解读 ✓ 训练建议 ✓ 记忆连续 ✓ 真流式 ✓ |
| 限制 | 无 Shell ✗ 无子代理 ✗ 无 MCP ✗（**佳明场景不需要** ✓） |
| 安全 | API Key 存设备侧 ✓（`preferences` ✓ 可加混淆 ✓）；不外发 ✓ |

### 方案 B · NAPI 嵌入 QuickJS（**不推荐** ✗）
- 可复用 JS 生态 ✗ 但需自建 NDK 工程 ✓ 交叉编译 ✓ 包体 +8~15 MB ✗ 崩溃面大 ✗
- 收益 vs 投入：**差** ✗

### 方案 C · 双轨（过渡期，**现状** ✓）
- 现在就是：App（展示/计算）+ 远程后端（对话/数据中转）✓
- 优点：已可用 ✓ 缺点：依赖后端在线 ✓ 体验受网络影响 ✗

## 五、设备侧 vs 后端侧 的职责重划（方案 A 后）

| 能力 | 现状（后端） | 方案 A（设备） |
|---|---|---|
| 佳明登录态 | 后端持有 `di_token` | **设备持有** ✓（更安全 ✓ 不经过服务器 ✓） |
| 活动/详情/轨迹 | 后端代理 | 设备直连 Garmin API ✓ |
| 功率曲线/爬坡/图表 | 后端算 + App 画 | **全部 App 内算** ✓（现在已大半在 App ✓） |
| 对话/LLM | 后端 `dsh headless` | **设备直连 LLM** ✓ 真流式 ✓ |
| 记忆/会话 | 后端 + App 缓存 | **设备本地** ✓ |
| 省电/后台 | 服务器 7×24 | 设备按需 ✗（无后台自动同步 ✗） |

**唯一实质损失** ✗：**没有 7×24 后台同步**（手机不开 App 就不更新 ✓）。
取舍建议 ✓：进 App 时增量同步（已有 ✓）+ 可选"后台任务"（HarmonyOS 受限 ✗ 仅短时 ✓）

## 六、风险与对策

| 风险 | 说明 | 对策 |
|---|---|---|
| **LLM Key 在设备上** | 反编译可提取 ✗ | ① 用**短生命周期 key** / 自建代理转发 ✗（又回到后端 ✗）② 或接受"个人使用"风险 ✓ ③ `preferences` + 简单混淆 ✓ |
| **Garmin 登录态在设备上** | 同上 | 设备侧本就更安全 ✓（不经过服务器 ✓）；加生物认证解锁可选 ✓ |
| **无后台同步** ✗ | 数据新鲜度依赖打开 App | 启动即增量拉 ✓ + 下拉刷新 ✓ + 首页显示"最后同步时间" ✓ |
| **审核风险** | 应用内含 LLM Key / 直连第三方 ✗ | 华为审核对"用户自带 Key"较友好 ✓；自建 Key 需说明 ✓ |
| **包体** | 纯 ArkTS 增加很小 ✓ | +200~400 KB ✓ |
| **维护双份** | 后端与设备两套逻辑 ✗ | 建议**一次性切换**到设备侧 ✓ 后端仅保留"开发调试"用途 ✗ |

## 七、迁移路径（建议 4 步）

1. **抽公共层**（1 轮）：把"佳明 API 调用 + 曲线/爬坡算法"抽成 ArkTS 模块 ✓（现在分散在页面里 ✗）
2. **设备侧 Agent 内核**（2~3 轮）：SSE 流式 ✓ tool-calling 循环 ✓ 记忆 ✓
3. **工具集**（1~2 轮）：`garmin.*`（活动/详情/趋势/HRV/身体电量 ✓）+ `memory.*`（读写会话 ✓）
4. **切流**（1 轮）：对话页从"后端 chat"切到"本地 Agent" ✓ 后端退为可选调试通道 ✓ 保留开关 ✓

## 八、结论

| 问题 | 答案 |
|---|---|
| 能把 DSH 塞进 App 吗 | **不能** ✗（无 Node 运行时 ✓ SDK 扫描证实 ✓） |
| 能做到"不再依赖后端"吗 | **能** ✓ 用**最小 Agent 内核**（纯 ArkTS ✓） |
| 值得做吗 | **值得** ✓✓ —— 尤其：**真流式** ✓ · **Key 不上服务器** ✓ · **断网也能看已有数据** ✓ |
| 主要代价 | 无后台同步 ✗ · 需要重写对话层 ✗（约 600~900 行 ✓） |

**建议**：按第七节 4 步走 ✓ 第 1 步（抽公共层）风险最低 ✓ 第 2 步收益最大 ✓
